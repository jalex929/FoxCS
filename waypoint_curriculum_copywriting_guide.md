# Waypoint Learning Curriculum Copywriting Guide

## Purpose

Use this guide when writing or revising curriculum copy for Waypoint Learning. It defines how instructional content should support diverse Learners, how the curriculum should sound, and how to write clear learning and language objectives using **“I can…”** framing.

Waypoint Learning is not only a content-delivery system. It is an adaptive learning environment designed to help Learners build understanding, confidence, and independence over time. Curriculum copy should therefore do more than explain concepts. It should reduce cognitive load, make thinking visible, normalize revision, and give Learners multiple ways to enter, practice, and demonstrate a skill.

---

## 1. Core Curriculum Writing Principles

### 1.1 Design for Learner variability from the beginning

Do not write for a single “average” Learner and add support later. Assume that Learners will differ in:

- prior knowledge
- reading fluency
- vocabulary familiarity
- confidence
- working memory
- processing speed
- attention and executive functioning
- comfort with abstraction
- familiarity with technology
- willingness to take risks
- ability to resume after an interruption
- need for repetition, examples, or challenge

Write the core experience so that it is understandable and usable across these differences.

### 1.2 Prioritize reasoning over memorization

Curriculum should help Learners understand:

- what a concept means
- why it matters
- how it works
- when to use it
- how to recognize it in a new context
- how to check whether their approach worked
- how to revise when it did not work

Definitions and syntax matter, but they should support reasoning rather than replace it.

### 1.3 Teach before assessing

Do not ask Learners to demonstrate knowledge that has not yet been clearly introduced, modeled, or practiced.

A typical instructional progression should be:

1. Connect to prior knowledge.
2. Introduce the new idea.
3. Model the thinking process.
4. Work through a guided example.
5. Provide supported practice.
6. Provide increasingly independent practice.
7. Check for understanding.
8. Prompt reflection, transfer, or revision.

### 1.4 Treat debugging, retries, and revision as learning

Waypoint should communicate that:

- mistakes provide useful information
- retries are evidence of persistence
- feedback is part of the learning process
- revision is expected
- debugging is a normal form of problem solving
- needing support does not mean a Learner is failing
- mastery may require multiple attempts

Avoid language that frames an incorrect answer as a personal deficiency.

### 1.5 Reduce unnecessary cognitive load

Curriculum copy should make the intended learning challenge clear without adding avoidable reading or interpretation demands.

Use:

- short paragraphs
- descriptive headings
- one primary idea at a time
- direct instructions
- consistent terminology
- concrete examples before abstract explanations
- visible steps for multistep processes
- reminders at the point of need
- concise summaries after complex explanations

Avoid:

- dense walls of text
- long introductions before the useful information
- unexplained jargon
- decorative language that obscures meaning
- multiple new concepts in one sentence
- directions that require Learners to remember several steps at once
- trick questions
- culturally specific assumptions that are not relevant to the skill

### 1.6 Make content interruption-tolerant

Learners may pause, become distracted, lose their place, or return later.

Write content so that a Learner can resume without rereading an entire lesson. Use:

- clear section headings
- brief recaps
- progress cues
- explicit references to the current task
- reminders of important variables, goals, or constraints
- self-contained content blocks
- consistent lesson structures

### 1.7 Build confidence without lowering rigor

Supportive curriculum is not vague, overly easy, or falsely congratulatory.

Good support:

- clarifies the task
- breaks complexity into manageable parts
- names successful thinking
- gives actionable feedback
- provides another path into the same concept
- preserves the intellectual goal
- gradually removes scaffolds

Do not confuse accessibility with reduced expectations.

## 2. Writing for Diverse Learners

### 2.1 Use multiple access points

When introducing an idea, provide more than one way to understand it when useful:

- a plain-language explanation
- a concrete example
- a visual or structural representation
- a worked example
- a comparison to a familiar idea
- a short opportunity to try the concept

Do not add multiple representations only for decoration. Each should clarify a different part of the concept.

### 2.2 Move from concrete to abstract

Introduce unfamiliar or abstract ideas through observable examples.

Preferred sequence:

1. Show what happens.
2. Name the pattern.
3. explain why it happens.
4. Introduce the formal term or rule.
5. Apply the idea in a new situation.

For programming content, show the behavior of the code before expecting the Learner to explain the abstraction.

### 2.3 Make hidden thinking visible

Do not only show a correct answer. Explain the decisions that produce it.

Model questions such as:

- What is the problem asking?
- What information do I already have?
- What can I break into smaller parts?
- What pattern do I notice?
- What detail can I temporarily ignore?
- What should happen first?
- How can I test this?
- What does the output tell me?
- What should I revise?

This supports computational thinking and helps Learners transfer strategies beyond a single problem.

### 2.4 Scaffold without over-explaining

A scaffold should help the Learner do the thinking, not do all of the thinking for them.

Possible scaffolds include:

- a partially completed example
- a step list
- a vocabulary reminder
- a sentence frame
- a narrowed set of choices
- a hint that points to the relevant concept
- a debugging prompt
- a smaller version of the original task
- a reminder of a related prior skill

Remove or reduce scaffolds as the Learner gains proficiency.

### 2.5 Distinguish the primary objective from supporting skills

A task may require several skills, but it should have one clear primary learning target.

When writing a task, identify:

- **Primary objective:** the new or central skill being assessed
- **Supporting skills:** previously learned skills needed to complete the task
- **Possible barriers:** reading, syntax, vocabulary, memory, navigation, or context demands that are not part of the primary objective

Do not let a supporting skill accidentally become the main reason a Learner cannot demonstrate the target skill.

### 2.6 Use accessible examples

Examples should be:

- age-inclusive
- culturally broad
- understandable without specialized background knowledge
- relevant to the concept
- respectful
- free of stereotypes
- usable by both high-school and adult Learners

Explain any context that is necessary to solve the problem.

### 2.7 Avoid deficit-based language

Do not describe Learners as lazy, weak, behind, careless, low, or bad at a subject.

Prefer language that describes current evidence or a next step:

- “This skill is still developing.”
- “You may need another example before trying this independently.”
- “Your current answer shows that you understand ____. Next, focus on ____.”
- “Let’s break this into smaller steps.”
- “Review how the condition controls whether the code runs.”

## 3. Voice and Tone

### 3.1 Overall voice

Waypoint curriculum should sound:

- warm
- clear
- calm
- encouraging
- respectful
- direct
- curious
- technically accurate
- learner-centered
- confident without sounding rigid
- supportive without sounding childish

Use **Learner** with a capital **L** when referring to the person using the curriculum. Do not use “user” in instructional copy. Avoid “student” when writing content intended for the broader Waypoint audience.

### 3.2 Speak to the Learner directly

Use second person when giving guidance:

- “You will compare two possible solutions.”
- “Run the code and observe what changes.”
- “Your next step is to test the condition.”

Direct address makes instructions easier to follow and keeps the experience active.

### 3.3 Be encouraging, but specific

Avoid generic praise such as:

- “Great job!”
- “Awesome!”
- “You’re a coding superstar!”

Prefer feedback that names what the Learner did:

- “You correctly updated the variable before printing it.”
- “Your condition checks the correct value.”
- “You identified the repeated pattern.”
- “Your revision fixes the order of operations.”

Encouragement should reinforce a strategy, decision, or demonstrated skill.

### 3.4 Normalize difficulty

Use language that makes productive struggle feel expected:

- “This idea may take more than one attempt.”
- “Try tracing one loop iteration at a time.”
- “It is normal to revise code after seeing the output.”
- “You do not need to solve the entire problem at once.”
- “Start with the smallest part you can test.”

Do not imply that concepts are universally easy.

Avoid:

- “This is simple.”
- “Obviously…”
- “You should already know…”
- “Just…”
- “As everyone knows…”

### 3.5 Maintain emotional neutrality around errors

Errors should be described as information.

Prefer:

- “The output does not match the goal yet.”
- “This condition becomes true earlier than intended.”
- “The variable is being updated in the wrong place.”
- “The error message points to line 6.”
- “Compare the current result with the expected result.”

Avoid:

- “Wrong.”
- “You failed.”
- “That makes no sense.”
- “You made a careless mistake.”
- “Incorrect again.”

### 3.6 Keep humor optional and nonessential

Light humor may support engagement, but a Learner should never need to understand a joke, reference, or idiom to understand the lesson.

Do not use humor that:

- mocks confusion
- relies on stereotypes
- makes errors feel embarrassing
- distracts from the task
- assumes shared cultural knowledge

## 4. Language Style Guidelines

### 4.1 Use clear, concrete wording

Prefer:

- “Create a variable named `score`.”
- “Check whether `score` is greater than 10.”
- “Print the message only when the condition is true.”

Avoid:

- “Leverage a variable to facilitate evaluation of the score.”
- “Utilize conditional logic in order to determine whether the threshold has been surpassed.”

### 4.2 Use consistent terminology

Choose one term for each concept and use it consistently.

For example:

- use “condition,” not alternating among “condition,” “test,” “check,” and “rule” unless the distinction is explicitly taught
- use “run the code,” not alternating among “execute,” “launch,” and “play” without reason
- use “output” when referring to what the program produces
- use “error message” when referring to system-generated error text
- use “attempt,” “feedback,” “revision,” “mastery,” and “progress” consistently when discussing the learning process

Introduce synonyms only when they are instructionally useful.

### 4.3 Define technical vocabulary at first use

A first-use explanation should include:

1. the term
2. a plain-language meaning
3. an example or observable behavior

Example:

> A **condition** is an expression that is either `True` or `False`. A program can use that result to decide whether a block of code should run.

### 4.4 Prefer active voice

Prefer:

- “The loop repeats the code.”
- “You will test the function.”
- “The program stores the value.”

Avoid unnecessary passive constructions:

- “The value is stored by the program.”
- “The function will be tested by you.”

Passive voice may be used when the actor is unknown or unimportant.

### 4.5 Keep sentences manageable

Aim for one main action or idea per sentence.

Instead of:

> Create a variable that stores the score and then write a condition that checks whether it is above 10 before printing a message that tells the player they have advanced.

Use:

> Create a variable that stores the score. Then check whether the score is greater than 10. If it is, print a message that tells the player they have advanced.

### 4.6 Write instructions in the order Learners should complete them

Do not make the Learner mentally reorder the task.

Preferred:

1. Create the variable.
2. Update its value.
3. Print the result.
4. Run the code.
5. Compare the output with the example.

### 4.7 Use formatting to support comprehension

Use:

- bold for important instructional language
- inline code formatting for code, variable names, values, filenames, and interface labels
- numbered lists for ordered steps
- bullets for unordered options or reminders
- tables only when comparison is clearer in rows and columns
- callouts for important warnings, tips, or recaps

Do not over-format. Emphasis should communicate hierarchy.

## 5. Computational Thinking in Curriculum Copy

Computational thinking should be introduced early and revisited throughout the course.

The five recurring practices are:

1. **Decomposition**
2. **Pattern Recognition**
3. **Abstraction**
4. **Algorithmic Thinking**
5. **Reflection and Revision**

### 5.1 Decomposition

Help Learners break a problem into smaller, workable parts.

Useful prompts:

- “What is one smaller part of this problem?”
- “Which part can you solve first?”
- “What information belongs in each step?”
- “Can you test one behavior before building the entire program?”

### 5.2 Pattern Recognition

Help Learners notice repetition, similarity, or structure.

Useful prompts:

- “What repeats?”
- “How is this example similar to the previous one?”
- “Which parts change, and which stay the same?”
- “What pattern could become a loop or function?”

### 5.3 Abstraction

Help Learners focus on relevant information and temporarily ignore unnecessary details.

Useful prompts:

- “Which details affect the result?”
- “What information can be represented with a variable?”
- “What can be generalized?”
- “Which details are part of the context but not part of the logic?”

### 5.4 Algorithmic Thinking

Help Learners create and evaluate ordered processes.

Useful prompts:

- “What should happen first?”
- “What sequence will produce the intended result?”
- “What decision does the program need to make?”
- “How could you write these steps so another person could follow them?”

### 5.5 Reflection and Revision

Help Learners evaluate evidence and improve an approach.

Useful prompts:

- “What did the output reveal?”
- “Which part worked as intended?”
- “Where did the result begin to differ from the goal?”
- “What is one change you can test?”
- “How did your revision improve the solution?”

## 6. Adaptive Curriculum Copy

Waypoint content may be delivered through Reinforce, Core, and Extend pathways and across increasing proficiency bands. Copy should remain consistent while changing the amount of support and complexity.

### 6.1 Reinforce

Purpose:

- rebuild prerequisite understanding
- reduce task complexity
- isolate one skill
- provide more guidance
- strengthen confidence through successful practice

Copy characteristics:

- shorter instructions
- more concrete examples
- fewer simultaneous decisions
- visible steps
- vocabulary reminders
- immediate, specific feedback
- smaller debugging targets

Do not make Reinforce content childish or punitive.

### 6.2 Core

Purpose:

- practice the current lesson objective at the expected level
- connect explanation to application
- build independent use of the skill

Copy characteristics:

- clear task goal
- moderate scaffolding
- opportunities to explain reasoning
- familiar and slightly varied contexts
- prompts to test and revise

### 6.3 Extend

Purpose:

- deepen reasoning
- introduce transfer
- combine the current skill with prior skills
- preview complexity that will later become expected

Copy characteristics:

- fewer procedural cues
- more open decision-making
- unfamiliar or less structured contexts
- comparison of approaches
- explanation, justification, or optimization
- transfer to a new problem type

Extend should add meaningful complexity, not merely more work.

### 6.4 Progression across proficiency bands

Complexity should generally progress through:

1. **Isolated use**  
   The Learner applies one skill in a direct context.

2. **Integrated use**  
   The Learner combines the skill with familiar supporting skills.

3. **Transfer**  
   The Learner recognizes when and how to use the skill in a new context.

4. **Synthesis**  
   The Learner selects, combines, explains, and evaluates multiple strategies.

An Extend task at one proficiency band may introduce a complexity that becomes baseline Core or Reinforce content at the next band.

## 7. Writing Learning Objectives with “I Can…” Framing

### 7.1 Purpose of an “I can…” objective

An “I can…” statement translates an instructional goal into language the Learner can understand, use, and reflect on.

A strong “I can…” objective should communicate:

- what the Learner will do
- the concept or skill involved
- the conditions or context when needed
- the expected level of performance

### 7.2 Learning objective formula

Use:

> **I can + measurable action + specific concept or skill + context or quality, when needed.**

Examples:

- I can create a variable and update its value.
- I can use a conditional statement to make a program respond to different inputs.
- I can trace a loop to determine how many times it will run.
- I can break a programming problem into smaller steps.
- I can compare two solutions and explain which one better meets the requirements.
- I can use test results to revise my code.

### 7.3 Use observable verbs

Preferred verbs include:

- identify
- describe
- explain
- compare
- classify
- create
- use
- trace
- predict
- test
- debug
- revise
- organize
- represent
- select
- justify
- evaluate
- design
- decompose

Avoid objectives built around internal or difficult-to-observe verbs unless paired with evidence.

Weak:

- I can understand variables.
- I can know how loops work.
- I can learn about functions.
- I can appreciate debugging.

Stronger:

- I can explain how a variable stores a value.
- I can trace a loop and predict its output.
- I can define and call a function.
- I can use an error message to locate a problem in my code.

### 7.4 Keep one primary target per objective

Avoid combining too many skills.

Overloaded:

> I can define variables, write conditions, use loops, debug errors, and explain how my program works.

Better:

- I can create and update variables.
- I can use conditions to control what a program does.
- I can use a loop to repeat a set of instructions.
- I can use evidence from the output to debug my code.
- I can explain how the major parts of my program work together.

### 7.5 Match the objective to the actual task

Do not write an explanation objective when the task only asks Learners to select an answer.

For example:

Objective:

> I can explain why a loop stops.

Aligned evidence:

- written explanation
- recorded explanation
- annotated trace
- comparison of two possible explanations

Not fully aligned:

- selecting the correct output without explanation

### 7.6 Write Learner-facing and author-facing versions

When useful, maintain both:

**Learner-facing objective**

> I can use a condition to make a program choose between two actions.

**Author-facing objective**

> Learners will construct and test an `if`/`else` statement that selects one of two outputs based on a Boolean condition.

The Learner-facing version should remain clear and concise. The author-facing version may include technical precision, assessment conditions, and standards alignment.

## 8. Writing Language Objectives with “I Can…” Framing

### 8.1 Purpose of language objectives

A learning objective identifies the concept or skill the Learner is developing.

A language objective identifies how the Learner will use language to access, discuss, explain, or demonstrate that learning.

Language objectives are especially useful for:

- multilingual Learners
- Learners developing academic vocabulary
- Learners who understand a concept but need support explaining it
- technical subjects with unfamiliar terminology
- activities requiring discussion, explanation, comparison, or justification

### 8.2 Language objective formula

Use:

> **I can + language function + key vocabulary or structure + communication context.**

Language functions include:

- describe
- explain
- compare
- sequence
- justify
- ask
- respond
- summarize
- interpret
- label
- define
- discuss
- write
- present

Examples:

- I can describe how a variable changes using the words **value**, **assign**, and **update**.
- I can explain the order of an algorithm using sequence words such as **first**, **next**, and **finally**.
- I can compare two code samples using **both**, **however**, and **while**.
- I can ask a debugging question that identifies what I expected and what actually happened.
- I can explain my revision using the words **attempt**, **feedback**, and **change**.
- I can summarize how repeated practice supports progress toward mastery.
- I can use the terms **condition**, **true**, and **false** to explain why a block of code runs.

### 8.3 Separate the content target from the language target

Example:

**Learning objective**

> I can use a loop to repeat an action a specific number of times.

**Language objective**

> I can explain how the loop changes each time using the terms **iteration**, **counter**, and **condition**.

The language objective should support the learning objective rather than introduce an unrelated writing or speaking task.

### 8.4 Identify the language demand of the task

Before writing the language objective, determine what the Learner must do with language.

Possible demands:

- read a technical explanation
- interpret an error message
- follow a sequence
- describe a process
- explain cause and effect
- compare solutions
- justify a choice
- ask for help
- summarize feedback
- reflect on progress

Write the objective around the actual demand.

### 8.5 Provide language supports when needed

Possible supports include:

- word banks
- sentence frames
- labeled diagrams
- model explanations
- examples and nonexamples
- partially completed responses
- transition-word lists
- vocabulary pop-ups
- opportunities to rehearse before writing
- acceptance of concise or multimodal responses when the objective does not require extended writing

Examples of sentence frames:

- “The variable changes from ___ to ___ because ___.”
- “First, the program ___. Next, it ___. Finally, it ___.”
- “Both solutions ___. However, the first solution ___ while the second solution ___.”
- “I expected ____, but the program produced ____. I will test ____.”
- “The condition is ___, so the program ___.”

Sentence frames should support expression without forcing every Learner into identical wording.

## 9. Success Criteria

Success criteria explain what meeting an objective looks like.

### 9.1 Write criteria that are observable

Objective:

> I can use a condition to control program behavior.

Possible success criteria:

- I write a condition that evaluates to `True` or `False`.
- I place the intended code inside the correct conditional block.
- I test at least two inputs.
- The program produces the expected result for each test.
- I revise the condition when the test results do not match the goal.

### 9.2 Keep criteria distinct from task directions

Task direction:

> Write a program that checks whether a player has at least 10 points.

Success criterion:

> The program produces the correct message for scores below, equal to, and above 10.

### 9.3 Use success criteria for self-assessment

Learner-facing reflection may use:

- I can do this independently.
- I can do this with a reminder or example.
- I am beginning to understand this.
- I need another explanation or smaller practice step.

Do not frame self-assessment as a permanent judgment of ability.

## 10. Feedback Copy

### 10.1 Feedback should be actionable

Useful feedback answers:

1. What did the Learner do?
2. What evidence shows progress or confusion?
3. What should the Learner examine next?
4. What is a manageable next action?

Example:

> Your loop repeats the correct code, but it runs one extra time. Check the loop boundary and compare the final counter value with the number of repetitions you want.

### 10.2 Use a progression of support

Feedback may move through:

1. **Notice**  
   Point to the relevant output, line, or behavior.

2. **Recall**  
   Remind the Learner of the concept or rule.

3. **Prompt**  
   Ask a focused question.

4. **Decompose**  
   Break the task into a smaller subproblem.

5. **Model**  
   Show a related example without completing the exact task.

6. **Reattempt**  
   Return the Learner to the original or an equivalent problem.

### 10.3 Do not reveal too much too quickly

A first hint should not usually provide the complete answer.

Preferred first hint:

> Compare the value of `count` before and after one loop iteration.

More explicit later hint:

> The loop should stop before `count` becomes 5. Check whether the comparison should use `<` or `<=`.

### 10.4 Name progress precisely

Prefer:

- “You selected the correct comparison operator.”
- “Your revised order now matches the required sequence.”
- “You found the line causing the error.”
- “You used the test result to update your approach.”

Avoid praise disconnected from evidence.

## 11. Lesson Copy Structure

A complete lesson may include the following authoring fields.

### Lesson overview

- lesson title
- lesson purpose
- relevance or real-world connection
- estimated scope or pacing guidance

### Objectives

- primary learning or programming objective
- computational thinking objective
- language objective
- Learner-facing “I can…” statements

### Preparation

- prerequisites
- prior skills used as scaffolding
- vocabulary
- common misconceptions
- accessibility considerations

### Instruction

- concept introduction
- plain-language explanation
- worked example
- modeled reasoning
- checks for understanding
- guided practice

### Practice

- Reinforce practice
- Core practice
- Extend practice
- spiral review
- vocabulary practice
- debugging or revision opportunities

### Evidence of learning

- success criteria
- mastery check
- transfer task
- reflection
- confidence self-assessment

## 12. Recommended Copy Patterns

### Introducing a concept

> A **function** is a named set of instructions that performs a task. Functions help you organize code and reuse instructions without rewriting them. In the example below, the function `greet()` prints a message each time it is called.

### Giving directions

> Complete these steps:
>
> 1. Create a variable named `lives`.
> 2. Set its value to `3`.
> 3. Subtract `1`.
> 4. Print the updated value.
> 5. Run the code and compare the output with your prediction.

### Prompting prediction

> Before you run the code, predict what it will print. Then run it and compare the result with your prediction.

### Prompting debugging

> The program runs, but the output does not match the goal. Identify the first point where the result differs from what you expected.

### Prompting decomposition

> Do not build the entire solution at once. First, write and test the part that checks the player’s score.

### Prompting reflection

> What did the output help you notice? Describe one revision you made and why you made it.

### Supporting a return after interruption

> You are working on using conditions to control what a program does. So far, you created the score variable. Next, write the condition that checks whether the score is at least 10.

## 13. Copy Review Checklist

Before publishing curriculum copy, confirm the following.

### Learner access

- [ ] The content does not assume unnecessary prior knowledge.
- [ ] Specialized context is explained.
- [ ] The main idea is visible early.
- [ ] Long processes are broken into manageable steps.
- [ ] The content can be resumed after an interruption.
- [ ] The task measures the intended skill rather than an unrelated barrier.
- [ ] Scaffolds support thinking without completing all of the thinking.

### Voice and tone

- [ ] The copy is warm, calm, respectful, and direct.
- [ ] The copy uses **Learner**, not “user.”
- [ ] The language does not sound childish.
- [ ] Difficulty and revision are normalized.
- [ ] Feedback is emotionally neutral and specific.
- [ ] Praise names an actual strategy or accomplishment.
- [ ] The copy avoids “obviously,” “simply,” “easy,” and “just.”

### Clarity

- [ ] Each sentence has one main purpose.
- [ ] Instructions appear in the order they should be completed.
- [ ] Technical terms are defined at first use.
- [ ] Terminology is consistent.
- [ ] Code and interface terms use appropriate formatting.
- [ ] Headings and lists make the structure visible.
- [ ] Examples directly support the learning goal.

### Objectives and alignment

- [ ] The lesson has one clear primary objective.
- [ ] The “I can…” statement uses an observable action.
- [ ] The language objective identifies an actual communication demand.
- [ ] Practice activities align with the stated objective.
- [ ] Success criteria describe observable evidence.
- [ ] The mastery check assesses the same skill taught in the lesson.
- [ ] Reflection asks Learners to examine strategy, evidence, or revision.

### Adaptive progression

- [ ] Reinforce content preserves dignity and rigor.
- [ ] Core content matches the expected lesson target.
- [ ] Extend content adds transfer or meaningful complexity, not only more work.
- [ ] Supporting skills do not overshadow the primary objective.
- [ ] Complexity progresses intentionally from isolated use to integration, transfer, and synthesis.

## 14. Claude Code Instructions

When generating Waypoint curriculum copy:

1. Follow this guide as the default curriculum style.
2. Refer to the audience as **Learners**.
3. Use clear, direct, age-inclusive language suitable for high-school and adult Learners.
4. Prioritize reasoning, computational thinking, debugging, revision, and transfer.
5. Write supportive copy without lowering rigor or overpraising.
6. Reduce cognitive load through concise paragraphs, visible structure, and ordered steps.
7. Introduce concepts before assessing them.
8. Define technical vocabulary at first use.
9. Separate the primary learning objective from supporting skills.
10. Include Learner-facing learning and language objectives using “I can…” framing.
11. Use observable verbs and align objectives, activities, feedback, and success criteria.
12. Normalize retries, pausing, feedback, and revision.
13. Avoid trick questions, deficit language, unnecessary jargon, and specialized assumptions.
14. For adaptive content:
    - Reinforce should isolate skills and increase support.
    - Core should target expected independent use.
    - Extend should deepen reasoning or transfer.
15. When writing feedback, identify evidence and provide one actionable next step.
16. When writing hints, begin with the least revealing support and increase specificity only as needed.
17. When writing complex tasks, model decomposition and make hidden thinking visible.
18. Preserve technical accuracy while using plain language.
19. Do not describe a concept as easy, obvious, or simple.
20. Review all generated copy against the checklist in this file.

## 15. Compact Prompt for Curriculum Generation

Use the following prompt when a shorter instruction is needed:

> Write this curriculum content in the Waypoint Learning voice. Address the audience as Learners. Use warm, direct, technically accurate, age-inclusive language that supports high-school and adult Learners with varied prior knowledge, confidence, reading fluency, processing speed, and executive functioning. Reduce cognitive load, define technical vocabulary, make reasoning visible, normalize debugging and revision, and avoid trick questions or deficit-based language. Teach before assessing. Identify one primary learning target, separate supporting skills, and align instruction, practice, feedback, and success criteria. Include a measurable Learner-facing learning objective and a language objective using “I can…” framing. Use Reinforce, Core, or Extend scaffolding appropriately, preserving rigor while adjusting support and complexity.
