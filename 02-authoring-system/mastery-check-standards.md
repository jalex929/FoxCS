# Mastery Check Authoring Standards

**Audited 2026-07-24, per Jay's request:** mastery-check authoring is already thoroughly documented in `adaptive-python` — `python-app/docs/content/mastery-check-schema.md` (module-level checks) and `python-app/curriculum/schemas/MASTERY_CHECK_LESSON_README.md` (lesson-level checks, plus a `MASTERY_CHECK_LESSON_TEMPLATE.tsv` reference). This is a port-and-scale-down, not a from-scratch build.

## What FoxCS keeps unchanged — genuinely good practice regardless of scale

- **Backwards design.** Write the mastery check *before* the lesson's practice content, not after. The mastery check defines what "done" actually looks like; practice questions are then authored to build toward it. Authoring order: (1) lesson objectives, (2) mastery check, (3) practice content. Authoring in the opposite order risks a mastery check that doesn't actually test what got taught.
- **One primary objective per item.** Every mastery-check question should point at exactly one skill_id (FoxCS's own term — see `objectives-and-skills-proficiency.md`) as its main target. This is what makes it feed the proficiency scale meaningfully instead of just being "a quiz."
- **Prefer deterministic validation.** Multiple choice, short answer with exact/normalized matching, predict-the-output — anything Moodle's Question engine can auto-grade natively. This matters *more* for FoxCS than it did for adaptive-python: there's no coderunner plugin installed on this Moodle instance (confirmed earlier) and no automated grading engine yet (`05-grader` isn't built), so every code-writing/open-ended item is a manual-grading cost against the 1-hour/week budget. Default to auto-gradable types for anything living in Moodle; save open-ended/code-writing checks for the VS Code side, consistent with the two-surface model.
- **Status lifecycle** — mapped onto FoxCS's existing `course-plan.md` legend rather than importing a second one: `draft` ≈ 🔄 in progress, `validated`/`review_ready` ≈ ✅ drafted, `published` ≈ 🔍 reviewed/final. Don't add a parallel status vocabulary.

## What FoxCS scales down or drops

- **Question count.** adaptive-python targets 8-12 items per lesson mastery check, 20-25 per module. That's on top of FoxCS's already-set 10-15-total-practice-items-per-lesson cap — don't stack a second large question set on top of an already-tight practice budget. **FoxCS default: 3-5 items per lesson mastery check.** Small, but each one should be a genuine synthesis/application check, not a recall repeat of a practice question already asked once.
- **Difficulty bands — kept, but as a label only, not a structure.** Reconciled 2026-08-04 (see `decisions-log.md`): in adaptive-python, `starter/skilled/legendary/mythic` is load-bearing — it's one axis of a 4-band × 3-lane routing matrix crossed with `question_complexity` and gated by `prerequisite_objectives` (`question-complexity-model.md`'s Handoff Rule). FoxCS can't take that structure — it's exactly the deep branching complexity the 2026-07-24 entry retired in favor of the shallow Reinforce/Core/Extend ladder (`objectives-and-skills-proficiency.md`), and there's no adaptive engine here to enforce band-to-band handoffs anyway. But Jay's read was that students responded to the *names* — so the vocabulary survives as a purely cosmetic, student-facing label, decoupled from any routing logic. **The internal authoring axis stays DOK** (that's what actually determines question design and feeds `dok_levels_covered`); a band name is just a skin optionally displayed on top. Convenient alignment: adaptive-python already restricts mastery checks to its two hardest bands only (`legendary`/`mythic` — never `starter`/`skilled`), which lines up naturally with FoxCS's own DOK 2-3 skew for mastery checks. So where a band label is wanted on a mastery-check item, use **DOK 2 → "Legendary"**, **DOK 3 → "Mythic"** — cosmetic only, no gating, no prerequisite matrix. `starter`/`skilled` aren't used in mastery checks here either, same as adaptive-python, though they remain available as optional flavor labels elsewhere (e.g. practice-item difficulty) if a future lesson wants them — not required now.
- **No separate unit-level mastery-check file.** adaptive-python has both a per-lesson mastery check and a per-module one, with the module-level version specifically testing cross-lesson synthesis. FoxCS already has a natural home for that role: **the Unit Project** (e.g. "Interactive Greeting" for Unit 01) already requires combining skills across the unit's lessons into one working program — that already *is* the cross-lesson synthesis check. A second, separate unit-level quiz on top of it would be exactly the kind of redundant volume the "avoid busy work, favor meaningful hands-on practice" principle (from the earlier practice-ladder discussion) argues against. **Recommendation: skip a distinct unit-level mastery-check file; the Unit Project carries that role instead.**

## Resolved: Moodle is the default surface

**Confirmed 2026-09-09**, once the first real per-lesson Mastery Checks were actually built (02.1, 02.2 — see `worklog.md`'s matching entry): **Moodle native Quiz is the default**, not a VS Code file. 3-5 items skewed DOK 2-3, mostly conceptual/predict-output/fix-the-line, auto-graded via shortanswer/multichoice. A VS Code-side item is still possible for a skill that genuinely can't be tested any other way, but it's the exception, not the default — see the rule immediately below before building one.

## Standing rule: no starter-file scaffolding for a VS Code Mastery Check item

**Added 2026-09-09, per Jay directly:** "VS Code likes to use intelligence to suggest lines of code. So I do not want to provide any starter context for Mastery Checks so they do not have comments that will recommend the structure to them/attempt to autofill code." If a Mastery Check item ever does need a VS Code-side component (rare, per the resolved default above), **do not give students a starter `.py` file with numbered-step comments, TODO markers, or any structural scaffolding** — unlike Coding Exercises and Practice, which are explicitly built with that pattern (see `vscode-content-conventions.md`). VS Code's built-in IntelliSense/autocomplete can use comment scaffolding as a prompt to suggest the actual answer, which defeats the point of an assessment. A VS Code Mastery Check item should be a blank file plus instructions given elsewhere (the Moodle quiz intro, not the file itself), or better, redesigned as a Moodle-native predict-the-output/fix-the-line item instead — check whether the skill can be tested that way before reaching for a VS Code file at all.

## Standing rule: Unit 01's essay-type items use a floor-of-80% ELL accommodation

**Added 2026-09-13, per Jay directly** — see `decisions-log.md`'s matching entry for full context. FoxCS has many English Language Learners who may genuinely engage with a Unit 01 essay-type mastery-check question without yet being able to fully articulate the answer in English. **For Unit 01's essay-type items specifically: any genuine, on-topic attempt scores no lower than 80%**, on a discrete 5-tier scale (80/85/90/95/100 — not a continuous range), not the harsher 0%-possible full/partial/no-credit judgment used elsewhere. This is scoped to Unit 01 only, not a change to the standard grading model in `../grade-point-scale.md`. **A response that only restates the question back (the 80-tier case) must get concrete remediation scaffolding in its feedback** — sentence starters/frames specific to that question, not generic "try again" language — so the student has something concrete to build from next attempt. A response that is truly blank, off-topic, or not a real attempt is not covered by this floor.

## Standing rule: submission-window check runs before content grading, and overrides the ELL floor

**Added 2026-09-14, per Jay directly.** Mastery Checks are not password- or time-gated (a gate can block the whole class, including a substitute without account access) — but before any response's content is graded for quality, its submission timestamp must be checked against the real class-period bell schedule (`05-grader/check-submission-windows.py`, currently Game I / 1st and 8th period only). A submission finished outside that window — beyond a 5-minute grace period past the period's official end, so a student finishing right at the bell isn't penalized — **gets no credit, full stop, regardless of content quality.** This is a procedural gate checked first, and it overrides even the Unit 01 ELL 80%-floor accommodation above: an out-of-window submission does not get the floor just because it was a genuine attempt.

## Standing rule: the quiz intro doesn't preview what's being tested

**Added 2026-09-09, per Jay directly**, after the 02.2-02.5 Mastery Check intros were found stating things like "recognizing them (including the disguised-whole-number case)" before students started the check. Jay's reasoning: "I want to know how they are doing... based on their exposure to the content" — an unprimed result, not one shaped by the intro itself telling them exactly which trick case to watch for. **A Mastery Check intro should say what lesson it's testing and how many questions, nothing more** — no sub-skill breakdown, no naming of specific edge/gotcha cases the questions will probe. Compare:

- Too much (fixed 2026-09-09): *"4 questions checking that you can apply what 02.3 taught about floats: recognizing them (including the disguised-whole-number case), choosing one on purpose, and predicting mixed integer/float arithmetic."*
- Right level: *"4 questions checking what 02.3 taught about floats. Ask your teacher for the password."*

This isn't a secrecy rule about the lesson's real objectives — those are already named to students during Instruction, where priming doesn't matter because there's no assessment happening yet. It's specifically about the moment right before a scored check: don't hand a preview of the answer key's shape along with the password reminder.
