2b. Block Builder with Distractor Pieces (harder variant)

New — demoed here first, not yet deployed in a real lesson
Added 2026-09 per Jay: a harder version of the block builder above, Duolingo-sentence-building style — the bank holds MORE pieces than the target line needs, so the student must also recognize and leave out the ones that don't belong, not just sequence the right ones. It's still a single correct/incorrect drill with exactly one anticipated right answer: Check compares the built line's text against one target string, the same exact-match logic as the plain Block Builder above. Distractor pieces are simply extra bank entries that never get used in a correct solution — no new grading logic, no partial credit, no separate distractor-detection step. Distractor-authoring rule: each distractor should be a genuine near-miss tied to a real misconception (here: a mismatched quote style, and a stray statement-terminator that doesn't exist in Python) rather than an unrelated random word — same "must not be guessable without engaging with the content" spirit as content-authoring-standards.md's multiple-choice distractor rule, just applied to pieces instead of options. The bank's shuffle is checked by the same check_shuffle_persistence.py scanner as any other block-bank — a distractor bank is still just a block-bank with more entries, nothing about it needs a different check.
Build the line: print("Level up!")
Not yet built into a real lesson — a good fit for a Reinforce/Extend-lane variant of an existing 01.x block-builder drill once one needs a harder version.

12. Password Gate + Automatic Hidden Timing

Live on every mastery check (timestamp mechanism redesigned 2026-08-07)
Not real security — a client-side pacing control. Try password DEMO01. Redesigned 2026-08-07: students used to copy a visible timestamp into their answer file by hand — Jay flagged that as a mistake in the original design. Now the unlock time writes automatically into a hidden field the moment the page unlocks; clicking "Mark Complete & Save" writes a second hidden completion time and saves the whole page in place. Both timestamps travel inside the submitted HTML file's own source for the grader to read — nothing for the student to transcribe or get wrong, and nothing visible cluttering the page. The hidden fields use a standard visually-hidden-but-DOM-present technique (clipped to 1px, aria-hidden) rather than literal white-on-white text, since color-matched text can still get selected, printed, or read by some accessibility tools — same goal, more reliable. Still not tamper-proof (a determined student could edit dev tools before saving) but far harder to get wrong by accident than hand-copying a time.
Unlocked. Read through, then click below when you're done — no timestamp to copy anywhere.
Reference: .../lesson_01_04_printing_output/09_mastery_check.html. Try it: unlock, click Mark Complete & Save, save the file, then open it and view source — both timestamps are in there.

13. Glossary Term (hover or click for a definition card)

New — demoed here first, not yet deployed in a real lesson
Underlined terms show a small definition card on hover. Clicking pins the card open — click the term again, click anywhere else, or press Escape to close it — which matters on touch devices where hover isn't reliable. Keyboard-accessible: Tab to the term, Enter or Space to toggle. The card clamps to stay inside the visible page (added 2026-08-07) — it won't run off the right edge, and flips above the term if there isn't room below. Proposed for Game of the Week pages (game-design vocabulary like mechanics, aesthetics) and for the first appearance of any major vocabulary term on an instructional page.

Before you start, make sure your mise en place is ready, then julienne the vegetables.

Not yet deployed — proposed for Game of the Week and first-use vocabulary on instructional pages.

14. Code Execution Stepper (simulated IDE)

New — demoed here first, not yet deployed in a real lesson
A simulated IDE view for walking through how code executes top to bottom — highlighting the current line, tracking variable state, and building up output one step at a time. Important: nothing here actually runs. Every step below is hand-authored in advance, same honesty as everywhere else in this library — this is closer to a comic strip of a program's execution than a real interpreter, which is exactly why the general "simulated IDE that matches typed code against accepted responses" idea got turned down (see decisions-log.md's 2026-08-08 entry) while this got built instead. The dropdown lets a student pick a value and see one of a few pre-written outcomes that match it — a curated branch, not a live recalculation. Play/Pause auto-advances at the chosen speed; the ◀ ▶ buttons step one at a time. The separate demo below shows the other piece — an "edit" animation, typed at randomized human-ish speed rather than a robotic fixed interval, for showing a debugging fix in progress.

15. Theme System (4-theme link, reconciled at Save)

New — demoed on a separate reference page, not yet deployed in a real lesson
Four student-selectable color themes: Light (default), Dark, and two new ones — Natural (cream/parchment background, deep green as the high-contrast color) and Synthwave/Cyber (deep blue/purple with neon accents, in the spirit of Cyberpunk 2077 and Stray). The persistent choice is a real <link id="foxcs-theme-link"> a student can hand-edit (survives across devices, unlike localStorage); a top-of-page selector previews instantly; Save reconciles the two by rewriting the link's href to match whatever's currently active. 16. Telemetry Event Log (hidden per-page interaction tracking)

New — demoed together with #15 above, not yet deployed in a real lesson
One hidden JSON blob per page (<script type="application/json" id="foxcs-telemetry">), generalizing the mastery-check's hidden-timestamp trick (#12 above) into a full append-only event log: theme changes, code-stepper play/pause/step/speed changes, hints revealed, every drill attempt (skill, lane, correct/incorrect, attempt number), and full Core/Reinforce/Extend lane transitions with a reason — not just the endpoint. It's what makes "did this student start at 1x speed and slow down, or never touch it" and "did Reinforce actually recover the skill" answerable from the saved file itself. Full schema, event types, the first-cut "stuck" heuristic, and the ingestion pipeline (rides the not-yet-built codename-swap script into 06-data-and-spreadsheets/telemetry/): ../telemetry-and-analytics.md.
Use the demo above: click through the theme selector and the Core/Reinforce/Extend arithmetic drill, then toggle "Show / hide" on its telemetry panel to watch events accumulate live. Real lesson pages never show this panel — it's a hidden field, surfaced here only so the mechanism can be reviewed.
Reusable mechanism: ../shared-styles/foxcs-telemetry.js (exposes FoxCSTelemetry.log() / .recordSave()). Not yet wired into any other component in this library (the stepper's own speed/play/step controls, drag-to-match, categorization, sequencing, etc. don't call it yet) — that's the natural next step once this mechanism itself is confirmed.

17. Code Hotspot (hover annotations + ordered step-through)

New — demoed here first, not yet deployed in a real lesson
Two ways to explore why specific keywords are there in a block of code — not what it executes (that's component #14), but why each piece of syntax was chosen. Hover or click any underlined keyword below for a definition card, same interaction pattern as the Glossary Term component (#13) — hover shows/hides automatically, click pins it open (matters on touch devices), Escape or click-elsewhere closes it, fully keyboard-accessible (Tab, Enter/Space). Or use the ◀ ▶ transport below the code to step through the same keywords in a fixed order, slideshow-style — each step highlights one keyword in the code and the explanation panel's content changes to match, rather than anything executing. The two mechanisms share the same state: clicking a keyword directly also moves the step position to match it. Demo content is C#'s public/private/void in a small Unity-style class — exactly the kind of thing worth a hover explanation the first time a Game II/Unity student sees it, per Jay's original request.

18. Code Block Multiple Choice

New — demoed here first, not yet deployed in a real lesson
Added 2026-09-04 per Jay: the standard treatment whenever a multiple-choice question's options are code, not short text. Each option is its own full <pre> block, stacked vertically, with a real radio input to the left of it rather than code crammed inline into a button label (the earlier ad hoc version of this, tried in the sandbox completion prototype, is the thing this pattern replaces). The whole row is one clickable label, so clicking anywhere on the code block selects it, not just the small radio circle. Selecting an option highlights it immediately (a lighter, non-graded "picked" state); the graded correct/incorrect color only applies after Check, same as every other component here.
Not yet deployed — first real fit is any Quick Check/Mastery Check question whose options are full lines of code (e.g. "which of these actually runs without an error"), in place of the inline-code-in-a-button style used ad hoc in the 2026-09-04 sandbox completion prototype.
